## 1. Executive Architecture & Evidence Synthesis

### 1.1 The Breakthrough: Context A vs. Context B Empirical Measurements
The empirical baseline established under ENG-OS-03C8 resolved the core mystery of the Jarvis 2.0 integration test blockage. By executing identical diagnostic probes across two controlled execution contexts using the exact same CPython 3.12.10 AMD64 runtime (`C:\Users\Youssef\AppData\Local\Programs\Python\Python312\python.exe`) under interactive desktop `Session 1, WinSta0\Default`, we isolated environmental boundaries from software defects:

- **Context A (Antigravity Developer Session):** Executed inside an AppContainer token (`TokenIsAppContainer == 1`, `IntegrityLevelRID == 0x1000` Low Integrity).
- **Context B (Host Windows Baseline):** Executed from an ordinary, non-elevated Windows PowerShell terminal (`TokenIsAppContainer == 0`, `IntegrityLevelRID == 0x2000` Medium Integrity, `TokenIsElevated == 0`). Context B passed all five mandatory acceptance gates audited by `tools/validate_context_b_gates.py` (`FINAL AUDIT VERDICT: ACCEPTED`).

The empirical contrast is stark and conclusive across core OS subsystems:
1. **Winsock Localhost Communication:** Non-blocking connect to `127.0.0.1` failed in Context A with `WSAEACCES (10013)` via `SO_ERROR`. In Context B, connect succeeded immediately with `SO_ERROR: 0` (`writable: True`).
2. **Python `socketpair()`:** CPython's Windows fallback `_fallback_socketpair` hung indefinitely in Context A during `lsock.accept()`. In Context B, `socket.socketpair()` succeeded cleanly in **2.20 ms**.
3. **asyncio Proactor Event Loop:** Initializing `asyncio.ProactorEventLoop()` hung indefinitely in Context A during `_make_self_pipe()`. In Context B, the Proactor loop initialized in **2.63 ms**, and test coroutine execution completed with return value `42`.
4. **Win32 AppContainer Process Creation:** Calling `CreateProcessW` with `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` (24 bytes) failed in Context A with Win32 Error `87` (`ERROR_INVALID_PARAMETER`). In Context B, the exact same native call with the identical ctypes structure succeeded in **5.33 ms** (`ok == True, last_error == 0`), and production launcher `spawn_suspended` succeeded cleanly (`error: None`).
5. **Restart Manager & TCP Tables:** `RmStartSession` failed in Context A with DWORD `29` (`ERROR_WRITE_FAULT`), and `GetExtendedTcpTable` failed with DWORD `5` (`ERROR_ACCESS_DENIED`). In Context B, `RmStartSession` succeeded in **2.35 ms** (DWORD `0`, `ERROR_SUCCESS`), and `GetExtendedTcpTable` returned DWORD `122` (`ERROR_INSUFFICIENT_BUFFER`) reporting valid table sizes across all 9 classes.
6. **Desktop Clipboard:** `OpenClipboard(0)` and `OpenClipboard(valid_hwnd)` failed in Context A with `last_error == 0`. In Context B under the identical interactive desktop (`WinSta0\Default`), both succeeded cleanly with `last_error == 0`.
7. **External DNS:** `getaddrinfo` failed in Context A (`[Errno 11001]`). In Context B, external DNS succeeded (`resolves: True`).

### 1.2 Epistemic Qualifications & Softened Findings
In accordance with strict engineering integrity and the independent architectural review, we enforce three explicit qualifications on these findings:

1. **AppContainer Ctypes Implementation:** The successful `SECURITY_CAPABILITIES` spawn in Context B is decisive evidence that the tested ctypes layout, parameter packing, and production launch path function correctly under Medium integrity. However, it does not prove that every edge-case AppContainer operation is bug-free. Furthermore, while the NT kernel prohibiting nested AppContainer token assignment from within an existing AppContainer parent token is the strongest architectural explanation, this mechanism remains a grounded engineering hypothesis. The formal finding is: *No defect was observed in the tested production AppContainer launch path under Context B. The failure is strongly associated with the Context A execution boundary.*
2. **Clipboard Access & Contention:** `OpenClipboard` succeeded in Context B and failed in Context A. However, `GetOpenClipboardWindow() == 0` does not conclusively prove that zero clipboard contention existed, because an application can open the clipboard without associating it with a valid HWND. While token window station permission dropping is the primary explanation, the exact mechanism remains unresolved until a controlled multi-process contention experiment is executed.
3. **Restart Manager Error 29:** `RmStartSession` succeeded in Context B (DWORD `0`) and failed in Context A with DWORD `29` (`ERROR_WRITE_FAULT`). The internal reason why the Windows Restart Manager service returns error 29 inside an AppContainer (e.g. RPC security binding restrictions, DCOM access permissions, or registry isolation) remains unresolved.

## 2. Profile A Design — Hermetic Development Profile

### 2.1 Mission & Operational Context
- **Execution Boundary:** Inside the Antigravity developer environment (AppContainer / Low Integrity, `BypassSandbox: false`).
- **Objective:** Provide fast, zero-flakiness, sub-100s feedback on unit logic, algorithms, state machines, and pure AST transformations during active development without requiring host OS privileges or out-of-sandbox elevation.

### 2.2 Scope & Safety Boundary
1. **Tier 1 Hermetic Unit Suite (1,237 nodes):** Fully operational today (1,228 passed, 0 failed, 9 skipped in 95.28s). Remains the foundational anchor of Profile A.
2. **Identified Mockable Async Tests:** Several suites currently categorized under Tier 2A/2B perform pure in-memory coroutine orchestration without needing live network endpoints (e.g. `test_streaming_tool_parser.py`, `test_phase5_p99_telemetry.py`, `test_document_provenance.py`, `test_p0_action_bound_authorization.py`). Under Profile A, these suites can execute reliably using deterministic in-memory mock transports and dummy event loops.
3. **Non-Mockable OS Suites Remain Blocked:** Suites that genuinely require live OS networking (e.g. Starlette ASGI servers, raw UDP telemetry listeners, live egress proxies) or Win32 process containment MUST NOT be run under Profile A. Instead of producing 30s watchdog hangs, the test supervisor in Profile A detects the missing capability during preflight and cleanly records `ENVIRONMENT_BLOCKED` with detailed diagnostic telemetry.

### 2.3 Strict Engineering Constraints for Profile A
- **No Monkey-Patching of `socketpair`:** Broad or monkey-patched replacements of `socket.socketpair` or `asyncio.windows_events._make_self_pipe` are strictly forbidden. CPython's IOCP Proactor loop relies on real OS file handles; artificial in-memory patches risk masking real concurrency race conditions and deadlocks.
- **No Weakening of Security Tests:** Tests asserting that untrusted input is rejected or that path traversal is prevented must NEVER have their assertions relaxed or bypassed to make them pass inside the sandbox.
- **Deterministic Test Doubles Only:** Where test doubles are used, they must be localized to specific test fixtures (e.g. mocking `urllib.request.urlopen` or patching `socket.getaddrinfo`), preserving the production codebase intact.

### 2.4 Profile Overlap & Immutable Execution Evidence Policy (Refinements D & E)
To ensure absolute reporting clarity, prevent double-counting, and eliminate mutable receipt file overwrites:

1. **One Canonical Node Identity:** Every test node possesses exactly one canonical identifier in `data/test_classification_manifest.json` (e.g. `tests/test_streaming_tool_parser.py::TestStreamingToolParser::test_token_parsing_stream`).
2. **Immutable Per-Run Execution Receipts (Evidence Engine Reuse):**
   - Replaces fixed file receipts with immutable records registered via Jarvis's existing evidence infrastructure (`tools/execution_evidence.py` and `data/execution_evidence/evidence_registry.db`).
   - Every run generates a unique execution receipt stored under `data/execution_evidence/receipts/` formatted as:  
     `EXEC-{YYYYMMDD}-{HHMMSS}-{PROFILE_TAG}-{HASH}.json`
   - Receipts immutably capture: execution ID, profile (`profile_a_hermetic`, `profile_b1_host_integration`, `profile_b2_interactive_desktop`), git commit SHA, context token integrity, elevation, desktop station, runtime interpreter, executed pytest node IDs, per-node outcome (`PASSED`, `FAILED`, `SKIPPED`, `ENVIRONMENT_BLOCKED`, `TIMED_OUT`), wall-clock duration, and stdout/stderr hashes.
3. **Authoritative Integration Result Precedence:** The authoritative integration outcome for any node declared in an integration tier comes strictly from the real integration profile. A successful hermetic mock result in Profile A **MUST NEVER** overwrite, substitute for, or mask a blocked or failing result in Profile B.
4. **Zero Double-Counting:** Aggregation into the whole-repository scorecard evaluates each test node exactly once under its designated authoritative tier. Running a test in both Profile A (as a mock unit) and Profile B (as a live integration test) generates distinct receipts without inflating total test counts beyond 2,206.

## 3. Profile B Design — Windows Host Integration Profile

### 3.1 Mission & Environmental Gates
- **Execution Boundary:** Non-elevated host Windows environment (local developer PowerShell or dedicated CI agent).
- **Objective:** Validate real Windows OS integration, kernel containment, Winsock loopback, asyncio pipelines, Restart Manager, and browser automation under real OS semantics.
- **Mandatory Environmental Gates:**
  * Primary process token (`TokenType == 1`, `TokenIsAppContainer == 0`).
  * Medium integrity level (`IntegrityLevelRID == 0x2000`).
  * Decisive non-elevation (`TokenIsElevated == 0`).
  * Exact matching CPython 3.12.10 AMD64 runtime.

### 3.2 Headless CI Evidence Boundary Grounding
> [!IMPORTANT]
> **Headless CI & Session 0 Are Unproven:**  
> Context B was measured strictly in: `Session ID: 1`, `Window Station: WinSta0`, `Desktop: Default`, `Integrity: Medium`, `Elevation: Not elevated`.  
> Standard headless CI agents and Windows background services frequently run in **Session 0**, which imposes distinct session isolation boundaries (e.g. lack of user desktop handles, restricted COM activation, and distinct LPC permissions).  
> Therefore, Profile B1 is strictly designated as a **Non-Elevated Windows Host Integration Profile**. Compatibility with Session 0 or headless CI services is **UNPROVEN** and treated as a separate, subsequent acceptance gate requiring dedicated empirical measurement (Stage 5 in Roadmap).

#### Profile B1: Host Non-Elevated Integration Profile
- **Target:** Host Windows PowerShell (Session 1). Headless CI / Session 0 compatibility is deferred to a dedicated experiment.
- **Supported Capabilities (Empirically Observed in Context B):**
  * Full asyncio Proactor event loops and `socketpair()`.
  * Winsock loopback TCP/UDP listeners and ASGI HTTP servers.
  * Win32 AppContainer process creation (`SECURITY_CAPABILITIES`).
  * Windows Restart Manager sessions and IP Helper TCP table inspection.
  * Real network SSRF integration testing against controlled test infrastructure.
- **Scope Breakdown:**
  * Tier 2A + Tier 2B: **474 nodes** ($273 + 201$)
  * Tier 3 (AppContainer & Restart Mgr): **32 nodes** ($29 + 3$)
  * SSRF Controlled Integration: **11 nodes**
  * Chromium Browser Integration: **9 nodes** (`CONDITIONALLY_BLOCKED`)
  * **Total Candidate Population:** **526 nodes** (all nodes excluding clipboard).
- **Crucial Invariant:** 526 represents the candidate population, **NOT** nodes currently proven executable or passing. Actual live execution under Profile B1 is strictly required.

#### Profile B2: Interactive Desktop Host Runner
- **Target:** Dedicated interactive developer desktop or active RDP session (`Session 1, WinSta0\Default`).
- **Supported Capabilities:**
  * Win32 Clipboard inspection and manipulation (`OpenClipboard`, `GetClipboardData`).
  * Native Windows UI Automation (pywinauto, UIA tree inspection).
  * Foreground window focus and synthetic input validation.
- **Scope:** 1 Tier 4 node (`tests/test_os_skills.py::test_clipboard_assistant`) plus interactive UIA suites.
- **Safety Preflight:** Profile B2 queries `GetProcessWindowStation()` and `GetThreadDesktop()`. If the session is non-interactive or Session 0, it halts immediately with `DESKTOP_INTERACTION_UNAVAILABLE` rather than failing spuriously.

### 5.2 Sequential Five-Gate Activation Sequence (Real Chromium-Owned Endpoint)
A generic WebSocket listener is **NOT** sufficient evidence of CDP functionality (it could accept connections without implementing the Chrome DevTools Protocol). The activation sequence requires connecting to the actual Chromium debugging endpoint:

1. **Gate 1: Executable Discovery & Win32 Creation Validation:**
   - Validate path `...\chrome-win\chrome.exe`, verify digital signature and Win32 executable headers, and confirm non-elevated process spawn capability.
2. **Gate 2: Bounded Process Startup Budget:**
   - Execute a bounded 15.0-second diagnostic probe (as an initial budget, not proof that longer startup cannot occur).
   - Capture complete telemetry: `stdout`, `stderr`, exit code, termination signal, and Crashpad named pipe status.
3. **Gate 3: Real Playwright Headless Launch Path:**
   - Execute Playwright's actual launch path: `playwright.chromium.launch(headless=True)` with production flags (`--headless=new`, `--disable-gpu`, `--no-first-run`, `--remote-debugging-port=0`).
   - Verify that Playwright successfully establishes its internal bidirectional driver communication.
4. **Gate 4: Real Chromium-Owned CDP Endpoint Verification:**
   - Discover the actual debugging port exposed by Chromium via `DevToolsActivePort` in the user data directory.
   - Establish a live WebSocket handshake directly to Chromium's DevTools URL.
   - Issue real CDP protocol commands (`Browser.getVersion`, `Target.getTargets`) and verify authentic Chrome JSON-RPC responses.
   - Execute a controlled local page interaction: navigate to a local controlled test page or `about:blank`, and evaluate JavaScript (`() => document.title`).
   - Navigation to arbitrary external third-party domains during diagnostic is strictly prohibited.
5. **Gate 5: Live Test Execution:**
   - Only upon passing Gates 1–4, authorize execution of the 9 browser integration nodes.

## 8. Security Threat Model & Scoped Job Object Containment (Refinement D)

1. **Zero Privilege Escalation:** Neither Profile A nor Profile B shall require Administrator privileges (`TokenIsElevated == 0`). Elevated execution is prohibited.
2. **Scoped Job Object Process Containment:**
   - The strict containment contract—spawning suspended (`CREATE_SUSPENDED`), assigning to a Win32 Job Object configured with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, and resuming—applies specifically to **untrusted or sandboxed child processes managed by Jarvis's production launcher** (`jarvis.skills.job_object_sandbox` / `jarvis.core.antigravity_bridge`).
   - This requirement is **NOT** imposed indiscriminately on standard test infrastructure subprocesses (such as `pytest` workers, Playwright driver node processes, or diagnostic tools) which utilize standard OS process management.
3. **Path Confinement:** File operations in both profiles must strictly validate paths against workspace boundaries via `validate_confined_path`.
4. **SSRF & Egress Protection:** Outbound network calls in Profile B must enforce `validate_egress_url` and socket-level IP pinning to prevent DNS rebinding.
5. **Inert Untrusted Data Defense:** All external telemetry, IPC inputs, and scraped webpage payloads must be tracked via `TurnTaintTracker` as untrusted inert data.
